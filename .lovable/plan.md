
# الدفع المختلط في سندات القبض والصرف (نقدي + شيكات)

## الوضع الحالي (بعد التدقيق)

- `vouchers.payment_method` قيمة واحدة فقط: `نقدي / تحويل / بطاقة / شيك`.
- في حال "شيك": يُنشأ قيد وحيد **مدين 1150 (شيكات برسم التحصيل) / دائن 1130**، وتُدخل الشيكات في جدول `cheques` (متعدد الشيكات مسموح).
- في حال "نقدي/تحويل/بطاقة": قيد وحيد مدين 1110/1120 / دائن 1130.
- **لا يوجد أي مسار لدمج نقدي + شيك في نفس السند** — يجب حالياً عمل سندين منفصلين.
- الـ RPCs المعتمدة: `create_receipt_with_entry` و `create_payment_with_entry` تقبل `p_cash_account_code` واحد فقط.

## الهدف

سند واحد للزبون/المورد يقبل توزيع المبلغ الإجمالي على **جزء نقدي (يودَع في صندوق أو بنك)** + **جزء شيكات (شيك واحد أو أكثر بأرقام وتواريخ استحقاق مختلفة)**، مع قيد محاسبي متعدد الأطراف صحيح، وسجل شيكات كامل، وتوافق مع تخصيص الفواتير (allocations) والإلغاء والتعديل.

## المخطط المحاسبي المطلوب

للقبض بمبلغ إجمالي X من زبون:

```text
مدين  1110/1120   = مبلغ الجزء النقدي (بحسب صندوق/بنك)
مدين  1150         = مجموع الشيكات المستلمة
    دائن  1130     = X (كامل مديونية الزبون)
```

للصرف: عكس ذلك مع 1160 (شيكات دفع مستحقة) بدل 1150، و2110 بدل 1130.
كل جزء يحمل نفس `contact_id` و`ref_number` وسند واحد في `vouchers`، ولكن **سطور متعددة في `voucher_lines`** وقيد `transactions` واحد (أو مجموعة قيود مرتبطة بـ `linked_transaction_id`).

## خطة التنفيذ

### 1) طبقة قاعدة البيانات (migration واحدة)

- إضافة عمود `vouchers.is_mixed boolean default false` وعمود `vouchers.mixed_breakdown jsonb` (توثيقي فقط — لا يُستخدم كمصدر حقيقة، المصدر هو `voucher_lines`).
- إنشاء RPC جديد `create_mixed_voucher_atomic(p_kind text /*receipt|payment*/, p_user_id, p_contact_id, p_contact_name, p_voucher_date, p_currency, p_exchange_rate, p_description, p_notes, p_reference, p_cash_parts jsonb, p_cheques jsonb, p_allocations jsonb, p_idempotency_key, p_cost_center_id, p_workshop_id, p_employee_id)`:
  - `p_cash_parts`: `[{ account_code: '1110'|'1120', cash_box_id, bank_account_id, amount }]` (يدعم صندوق + بنك في نفس السند لاحقاً).
  - `p_cheques`: `[{ number, date, bank, amount, account_number, notes }]`.
  - يتحقق: `sum(cash_parts.amount) + sum(cheques.amount) = p_total` (يُحسب داخلياً) — لا حاجة لإرسال total من الواجهة.
  - داخل transaction واحدة: إنشاء صف `vouchers` + سطور `voucher_lines` (سطر لكل part نقدي + سطر تجميعي 1150/1160 + سطر مقابل 1130/2110) + إنشاء صفوف `cheques` بحالة "مسجل" مرتبطة بـ `voucher_id` و`contact_id` + قيد `transactions` واحد بمجموع القيمة + تخصيص فواتير عبر `allocate_voucher_to_invoices_atomic` (إن وُجد).
  - Idempotency عبر `idempotency_key` كما بقية الـ RPCs.
- توسيع `update_voucher_atomic` ليعالج `p_kind='mixed'`: حذف السطور القديمة، وحذف الشيكات ذات الحالة الآمنة فقط (`مسجل`) عبر نفس منطق `voucher-cheques-sync.ts`، ثم إعادة الإنشاء.
- توسيع `void_voucher_atomic` ليعكس تلقائياً أي شيك ما زال بحالة "مسجل" ويرفض الإلغاء إن كان أي شيك دخل دورة حياة (مودع/محصل/مرتجع/مجيّر) — مع رسالة واضحة.
- منح `EXECUTE` للـ RPC الجديدة لـ `authenticated`.

### 2) واجهة `VoucherFormPage.tsx`

- إضافة خيار جديد بجانب "نقدي / شيك / تحويل / بطاقة" اسمه **"مختلط (نقدي + شيكات)"** (`paymentMethod = "مختلط"`).
- عند اختياره تظهر لوحة واحدة فيها:
  - قسم "الجزء النقدي" بمبلغ + اختيار صندوق أو بنك (يُعاد استخدام نفس المكونات الحالية).
  - قسم "الشيكات" بنفس المصفوفة `cheques[]` وواجهة الإضافة الحالية.
  - **شريط ملخّص** يعرض: نقدي + شيكات = الإجمالي (يُحدَّث لحظياً)، وعداد تحذير أحمر إن لم يتساوَ الإجمالي مع مبلغ السند/الفاتورة المخصَّصة.
- زر الحفظ يستدعي `create_mixed_voucher_atomic` بدل المسار الحالي عندما `paymentMethod === "مختلط"`.
- منع "مختلط" مع طرق ليست 1110/1120 (بطاقة/تحويل تبقى وحدها لأن قيدها البنكي مختلف).

### 3) الطباعة والعرض

- تحديث قالب الطباعة الرسمي `buildOfficialVoucher.ts` بحيث في حال `is_mixed=true`:
  - يُظهر جدول "تفاصيل الدفع" بسطرين: نقدي (المبلغ + الجهة) + شيكات (عدد + إجمالي).
  - يبقي جدول الشيكات التفصيلي الحالي كما هو.
- في شاشة العرض/التعديل: عند القراءة، إن كان `is_mixed` تُعبّأ الحقول من `voucher_lines` + جدول `cheques`.

### 4) الربط مع الفواتير والكشوفات

- `allocate_voucher_to_invoices_atomic` يبقى كما هو — يعمل على مجموع السند بغضّ النظر عن مكوّناته.
- كشف حساب الزبون سيعرض حركة واحدة بالمبلغ الإجمالي (سطر 1130 المفرد يضمن ذلك).
- شاشة الشيكات ترى الشيكات مرتبطة تلقائياً بالسند عبر `voucher_id` الموجود أصلاً في `cheques`.

### 5) اختبار QA (يدوي بعد التنفيذ)

1. سند قبض مختلط 500 نقدي + شيكين 300 و200 لزبون: التحقق من قيد واحد إجمالي 1000، وسطر 1130 دائن = 1000، وسطرَي 1110 (500) و1150 (500).
2. تعديل السند: تغيير مبلغ الشيك من 300 إلى 350 وزيادة النقدي إلى 550 → التأكد من إعادة إنشاء سليمة وعدم تكرار الشيك في جدول `cheques`.
3. محاولة إلغاء السند بعد إيداع أحد الشيكات → يجب أن يُرفض برسالة واضحة.
4. تخصيص السند على فاتورتين مختلفتين → `payment_invoice_links` صحيحة.
5. نفس السيناريو لسند صرف مع 1160/2110.
6. طباعة السند: الملخّص يعرض التوزيع بشكل صحيح.

### 6) مخاطر ومحاذير

- **لا مساس** بالمسارات الحالية (نقدي فقط أو شيك فقط) — الـ RPC الجديد مسار مستقل.
- Feature flag اختياري: `vouchers_allow_mixed` في `company_settings.feature_flags` (افتراضي ON للملكي، OFF لباقي المستأجرين حتى الاختبار).
- التعديل والإلغاء يمرّان عبر نفس دوال حماية الشيكات الموجودة (`SAFE_STATUSES`) لضمان عدم كسر أي شيك دخل الدورة المصرفية.
- Idempotency صارم لمنع الإنشاء المزدوج عند بطء الشبكة.

## المخرجات النهائية

- Migration واحدة (RPC جديد + عمودان + توسعة update/void).
- تعديلات على `VoucherFormPage.tsx` و`buildOfficialVoucher.ts` و`voucher-rpc.ts`.
- لا تعديل على منطق التخصيص/كشف الحساب/سجل الشيكات — كلها تعمل كما هي.
