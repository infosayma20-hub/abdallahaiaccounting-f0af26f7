# خطة معالجة الملاحظات — بحذر شديد ومراحل مستقلة

سبب التدرج: عندنا **990 ملاحظة linter** و**قاعدة بيانات إنتاج نشطة** فيها 180+ جدول و440+ دالة. التنفيذ دفعة واحدة خطر جدًا — أي تغيير على View أو RLS Policy ممكن يوقف شاشات كاملة. لذلك نقسم على مراحل، كل مرحلة قابلة للتحقق والتراجع.

---

## المرحلة 1 — الأداء (آمنة تمامًا، أثر فوري)
إضافة فهارس فقط. لا تغيير سلوك، لا تغيير سكيمة.

**الفهارس المقترحة (مبنية على slow_queries الفعلي):**
- `transactions (user_id, transaction_date, created_at) WHERE is_deleted = false` — يحل الاستعلام رقم 2 (1.4 ثانية معدل)
- `contacts (user_id, is_active, contact_name)` — يحل الاستعلام رقم 3 (830ms معدل)
- `order_item_modifiers (order_line_id)` — يخفف حمل الـ trigger على الإدراج
- فحص EXPLAIN قبل وبعد كل فهرس للتأكد من الاستخدام

**المخاطر:** شبه معدومة. الفهارس تُنشأ بدون قفل جداول ثقيل (حجم القاعدة 493MB فقط).

---

## المرحلة 2 — تدقيق Security Definer Views (8 أخطاء)
**قبل أي تعديل**: أستخرج قائمة الـ 8 views وأفحص كل واحد:
- من ينشئها؟ لماذا SECURITY DEFINER؟
- من يستخدمها في التطبيق (grep على الكود)؟
- هل بديل SECURITY INVOKER يعطي نفس النتيجة مع RLS الصحيحة؟

**التنفيذ:** لكل view على حدة، مع اختبار الشاشة المرتبطة قبل الانتقال للتالية. **لا تحويل جماعي.**

**المخاطر:** متوسطة — بعض الـ views ممكن تكون مقصودة (مثلاً `pos_orders_effective` الي أنشأناه سابقًا لتوحيد حالة الطلبات). سنُبقيها إذا كان الاستخدام محصور بـ security definer functions.

---

## المرحلة 3 — RLS Policies "USING (true)"
- أستخرج القائمة الكاملة من الـ linter
- أصنفها: (أ) مقصودة عامة، (ب) خطأ حقيقي على UPDATE/DELETE، (ج) على INSERT
- الفئة (ب) و(ج) هي الأخطر — أستبدلها بشرط `dataOwnerId` أو `company_id` حسب معمارية العزل متعدد المستأجرين

**المخاطر:** عالية إذا نُفذت بلا تدقيق. أي سياسة خاطئة تكسر الشاشة فورًا. **لهذا لكل جدول: قراءة السياسة → فهم من يكتب فيه → تعديل → اختبار.**

---

## المرحلة 4 — Function Search Path Mutable
تعديل ميكانيكي وآمن: إضافة `SET search_path = public` لكل دالة مفقودة. لا يغير المنطق.
- عبر migration واحدة بـ `ALTER FUNCTION ... SET search_path = public`
- لا لمس دوال `auth/storage/realtime/vault`

**المخاطر:** منخفضة، لكن العدد كبير (يحتمل 300+ دالة). سأنفذها دفعات من 50.

---

## المرحلة 5 — تنظيف Rolled-back transactions
تحقيق: 5.4M عملية مُلغاة تراكميًا. ابحث في postgres_logs عن الأخطاء المتكررة (غالبًا duplicate keys من شاشات retry). إصلاح المصدر لا العَرَض.

---

## القرار المطلوب منك

أقترح **البدء بالمرحلة 1 فقط الآن** — أضمن تحسين فوري 0% مخاطرة، وبعدها نناقش المرحلة 2. الخطة الكاملة (المراحل 2–5) تحتاج جلسات منفصلة كل واحدة قد تستهلك 20-40 عملية تعديل.

**بدائل:**
- **أ. المرحلة 1 فقط الآن** (موصى به) — فهارس الأداء، ~10 دقائق.
- **ب. المرحلة 1 + 4 معًا** — الفهارس + search_path fix (كلها آمنة ميكانيكيًا).
- **ج. تنفيذ كل المراحل تباعًا في هذه الجلسة** — خطر، طويل جدًا، وممكن نصطدم بمشاكل تحتاج قرار منك في المنتصف.

اختر أ أو ب أو ج، أو حدد أولوية مختلفة.
