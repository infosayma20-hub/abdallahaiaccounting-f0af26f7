## الهدف
حصر **المرتجعات** و**تعديل الدفعات بعد الإغلاق** بـ **وضع المدير** فقط، بحيث الكاشير ما يقدر يصل لأي عملية ترجع فلوس للزبون أو تعدّل دفعة محفوظة.

## السلوك المطلوب

### 1) زر "مرتجع" في سجل الفواتير
- يظهر دائماً، لكن عند الضغط:
  - إذا **وضع المدير غير مفعّل** → يفتح `ManagerVerifyDialog` (بصمة/PIN مدير) قبل فتح `ReturnDialog`.
  - إذا **وضع المدير مفعّل** → يفتح `ReturnDialog` مباشرة.
- نفس الحماية تنطبق على المرتجع الكلي والجزئي.

### 2) تعديل دفعة بعد الإغلاق (الحالة الجديدة)
- خيار جديد داخل `InvoiceHistoryDrawer` اسمه **"تعديل دفعة / استرداد جزئي"**.
- يظهر فقط في **وضع المدير**؛ مخفي تماماً عن الكاشير.
- يفتح حواراً (`PaymentAdjustmentDialog`) يعرض:
  - الدفعات الأصلية (مثلاً: 64 فيزا).
  - حقل **قيمة الاسترداد** + **طريقة الاسترداد** (نقدي/فيزا/تحويل).
  - **سبب التعديل** (إجباري).
- يستدعي RPC جديدة `adjust_pos_payment_manager` تقوم بـ:
  - إنشاء صف `pos_payments` بقيمة سالبة (refund line) — يتطلب تخفيف قيد `amount_positive` ليسمح بـ `amount < 0` فقط عندما `is_refund = true`.
  - تعديل `pos_orders.total` (اختياري حسب نوع التعديل: استرداد فقط مقابل تخفيض إجمالي).
  - ترحيل قيد محاسبي معاكس متوازن: مدين "مرتجعات مبيعات" / دائن حساب الاسترداد (1110 صندوق أو 1120 بنك).
  - تسجيل في `pos_sensitive_actions_log` مع `manager_user_id` والسبب.

### 3) فرض على مستوى قاعدة البيانات
- RPC الجديدة + RPC `process_pos_return` تفحص أن المستدعي عنده "Manager Mode Session" نشط (عبر `pos_sessions.manager_mode_until > now()`) أو دور Admin/Branch Manager. إذا لا، ترفض مع رسالة واضحة.
- هذا يضمن ما يحدث "Bypass" حتى لو حد عبث بالواجهة.

### 4) واجهة الكاشير
- إخفاء زر "مرتجع" تماماً من سجل الفواتير عند الكاشير العادي خارج وضع المدير، واستبداله برسالة "اطلب من المدير تفعيل وضع المدير لإجراء مرتجع".
- لا تغيير على إتمام البيع العادي ولا على الدفع المختلط.

## مثال: حالة الـ 64→57 فيزا
1. الكاشير يطلب المدير → المدير يفعّل **وضع المدير** (60 ثانية).
2. سجل الفواتير → الفاتورة → **تعديل دفعة / استرداد جزئي**.
3. قيمة الاسترداد = 7 ₪، طريقة = نقدي، السبب = "تعديل سعر بعد الدفع".
4. النظام:
   - يضيف صف `pos_payments` (visa +64) ثابت + صف جديد (cash −7, is_refund=true).
   - يعدّل إجمالي الطلب من 64 إلى 57.
   - يرحّل قيد: مدين مرتجعات مبيعات 7 / دائن صندوق 7.
   - عند إغلاق الوردية: المتوقع نقدي ينقص 7 ✅، الفيزا تبقى 64 ✅.

## الجوانب التقنية (للمراجعة)

- **ملفات أمامية:**
  - `src/components/pos/InvoiceHistoryDrawer.tsx` — gate زر المرتجع + إضافة زر "تعديل دفعة" تحت وضع المدير.
  - جديد: `src/components/pos/PaymentAdjustmentDialog.tsx`.
  - `src/hooks/usePOSManagerMode.ts` — استخدام `isManagerActive` كمصدر وحيد للحالة.

- **Migrations:**
  - تعديل قيد `pos_payments_amount_positive` ليصبح `amount > 0 OR is_refund = true` (إضافة عمود `is_refund boolean default false` + `adjustment_reason text` + `manager_user_id uuid`).
  - RPC `adjust_pos_payment_manager(p_order_id, p_amount, p_method, p_reason)` — تفحص صلاحية المدير، تنشئ صف refund، تعدّل `pos_orders.total`، تنشئ Transaction متوازن، تسجل في `pos_sensitive_actions_log`.
  - تحديث `process_pos_return` لإضافة فحص "Manager Mode active" بدل السماح للكاشير.

- **بدون كسر:**
  - لا تغيير على `complete_pos_order` ولا على شاشة البيع.
  - الفواتير القديمة + سجلات الدفع الموجودة تبقى كما هي (الـ default `is_refund=false`).
  - حسابات إغلاق العهدة (`shift-close-math.ts`) تتعامل تلقائياً مع صفوف refund لأنها تجمع `amount` بالعملة (السالب ينقص المتوقع).

## QA
- مدير يعمل استرداد 7 نقدي على فاتورة 64 فيزا → الإجمالي 57، الصندوق ينقص 7، الفيزا ثابتة، قيد متوازن.
- كاشير عادي يحاول الضغط على "مرتجع" → يطلب وضع المدير.
- كاشير عادي ينادي RPC مباشرة (test) → ترفض بـ "صلاحية مدير مطلوبة".
- إغلاق وردية بعد التعديل → variance = 0 لو الكاش الفعلي يطابق المتوقع الجديد.
