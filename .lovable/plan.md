
# الدفع المختلط (Split Payment) — نقدي + فيزا

## ١. الوضع الحالي (من فحص قاعدة البيانات والكود)

✅ **جيد:** جدول `pos_payments` أصلاً ما عنده قيد على `order_id` — يعني يقدر يقبل عدة صفوف لنفس الطلب (تقنياً جاهز).

❌ **المشاكل اللي لازم تتحل:**

1. **الواجهة (`POSPage.tsx`):** تخزّن `paymentMethod` واحد (`useState<string>("cash")`). الكاشير يختار طريقة وحدة فقط.
2. **دالة المحاسبة `complete_pos_order` (في عدة migrations):** تنشئ صفوف `pos_payments` لكل عنصر في الـ array (loop موجود)، **لكن قيد اليومية تنشئه مرة واحدة فقط بناءً على `p_payments->0`** (أول عنصر). يعني لو بعتنا نقدي + فيزا → الفاتورة كلها بتترحّل على الصندوق فقط ويختفي الفيزا من اليومية. **هاي أخطر نقطة.**
3. **العملات الأجنبية:** Logic الـ `foreign_amount` و `exchange_rate` مبنية على tender واحد.
4. **الكاش درج والباقي:** يفتح للكاشير فقط، والباقي يحسب على المبلغ المسلَّم. لازم ينحصر على الجزء النقدي فقط.
5. **إغلاق الوردية (`shift-close-math`):** ✅ هذي شغّالة صح — تجمع من `pos_payments` بحسب الطريقة. ما تحتاج تعديل.
6. **الإيصال / الطباعة:** يطبع طريقة دفع واحدة. لازم يعرض السطرين.

## ٢. القرارات الأساسية (مبنية على المنطق المحاسبي)

| البند | القرار | السبب |
|---|---|---|
| العملات في split | **ILS فقط في المرحلة الأولى** | خلط فيزا بدينار + نقدي بدولار = كابوس exchange rates. نضيفه لاحقاً. |
| طرق الدفع المسموح خلطها | **نقدي + فيزا** فقط (يقدر يكون عدة فيزا لو في أكثر من حساب بنكي) | باقي الطرق (آجل / حساب موظف) إفرادية بطبيعتها — لا يصح خلطها مع cash لأن آلية ترحيلها مختلفة. |
| الباقي (change) | يحسب من الجزء النقدي فقط، لا يتأثر بالفيزا | الفيزا = مبلغ مضبوط بدون tendered/change. |
| الترتيب على الإيصال | يطبع كل tender كسطر منفصل تحت "تفاصيل الدفع" | شفافية للزبون والمحاسب. |
| القيد المحاسبي | **سطرَي مدين منفصلين** في نفس قيد اليومية: Cash Box للنقدي + Visa GL للفيزا، مقابل دائن واحد للإيرادات | يحافظ على تكامل الميزان وعلى تتبع كل بنك على حدة. |
| الحد الأدنى لكل جزء | 0.01 — أي قيمة موجبة. ممنوع جزء = صفر. | يمنع إنشاء صفوف فارغة. |
| التحقق | مجموع كل الأجزاء = إجمالي الفاتورة بدقة ±0.01 شيكل | يمنع overpay/underpay. |

## ٣. الخطة بالتفصيل

### المرحلة A — قاعدة البيانات (Migration)

**1.** تعديل دالة `complete_pos_order` (في `pos_accounting_integrity_patch`) — هي العقدة الأهم:

```text
بدل: قراءة p_payments->0 فقط
صار: 
  - استخراج method + amount + visa_gl_account_code لكل عنصر
  - تحضير قائمة "tender lines" لكل tender (مدين Cash Box أو مدين Visa GL)
  - في قيد اليومية: 
       Dr Cash Box  (مجموع النقدي)
       Dr Visa GL   (مجموع الفيزا — قد يكون عدة حسابات)
       Cr Revenue   (الصافي بدون VAT)
       Cr VAT       (الضريبة)
  - idempotency_key يبقى POS-ORDER-{id} (واحد لكل طلب)
```

**2.** إضافة CHECK constraint بسيط على `pos_payments`: `amount > 0`.

**3.** إضافة عمود `card_reference TEXT` (اختياري) لتخزين آخر 4 أرقام / Approval Code من إيصال الفيزا.

**لن** نعدّل جدول `pos_orders` — حقل `payment_method` فيه يبقى للتوافق القديم ويُملأ بقيمة موحّدة `"mixed"` لما يكون split (أو بطريقة الدفع الوحيدة لو ما في split).

### المرحلة B — Hook + State للأجزاء

ملف جديد `src/hooks/usePOSTenders.ts`:
- `tenders: { method: 'cash'|'card'; amount: number; visaGlAccountCode?: string; reference?: string }[]`
- helpers: `addTender`, `updateTender`, `removeTender`, `clearTenders`
- محسوبات: `paidTotal`, `remaining`, `isBalanced`, `cashPortion`, `cardPortion`

### المرحلة C — واجهة الدفع المختلط

**في شاشة الدفع الحالية:**
1. تبقى الأزرار الكبيرة (نقد / فيزا / آجل / حساب موظف) كما هي للسرعة (one-tap = full amount).
2. زر جديد صغير "**دفع مختلط ✂️**" يفتح لوحة Tenders:
   - عرض المتبقي بخط كبير أحمر/أخضر.
   - زرّان: ➕ نقد ، ➕ فيزا (مع dropdown لحساب الفيزا لو في أكثر من حساب بنكي للبطاقة).
   - كل tender = صف فيه: المبلغ (قابل للتعديل) + ❌ حذف.
   - زر "**اقسم المتبقي**" يضع المتبقي كنقدي تلقائياً.
   - زر "إكمال البيع" مغلق إلا لما `remaining == 0`.
3. لو tender واحد فقط → نمرّر للـ RPC كـ payments array بطول 1 (متوافق مع السلوك الحالي تماماً).

### المرحلة D — الـ Offline Path

`createOfflineSale` يقبل أصلاً `offlinePayments` array. نوسّعها لتدعم الأجزاء، ولما يصير sync، الـ RPC المعدّل (المرحلة A) يتعامل معها تلقائياً.

### المرحلة E — الإيصال والطباعة

في `ReceiptTemplate.tsx` و `pos-print.ts`:
- لو `payments.length > 1`: نعرض قسم "تفاصيل الدفع" يلي سطر سطر (مثلاً: `نقد: ₪50.00 | فيزا (بنك فلسطين): ₪77.50`).
- لو واحد فقط: يظل كما هو (لا تغيير في الإيصالات الحالية).

### المرحلة F — تقارير الوردية و Invoice History

- `InvoiceHistoryDrawer` و `PosInvoiceDetailPage`: يعرضوا كل tenders.
- إغلاق الوردية: لا تغييرات (شغّالة أصلاً بحسب الفحص).
- شارة Method في القوائم: لو mixed → نعرض "مختلط 💳💵".

- تعديل دفعات بعد الترحيل (حالياً لازم Void + إعادة).

## ٥. مخاطر وخطة الاختبار

| الخطر | الإجراء الوقائي |
|---|---|
| القيد المحاسبي يطلع غير متوازن | Migration يبني الأسطر داخل CTE ويتحقق من توازنها قبل INSERT |
| الفاتورة القديمة بطريقة واحدة تكسر | نحافظ على نفس بنية `p_payments` (array) وسلوك العنصر الواحد مطابق 100% |
| Offline sync يعيد إنشاء فاتورة بـ tender واحد بدل اثنين | اختبار يدوي على scenario: نقدي 50 + فيزا 77.50، أوفلاين، ثم سنك |
| الكاشير يضغط Visa بالخطأ بنية split | الزر منفصل تماماً "دفع مختلط" — مفيش طريقة عرضية تدخلك للوضع |

**اختبارات إلزامية قبل النشر:**
1. بيع 100 شيكل = 60 نقدي + 40 فيزا → يطلع قيدين مدين منفصلين + سطر VAT + سطر إيرادات.
2. بيع 50 شيكل فيزا واحدة → سلوك مطابق للحالي (regression).
3. إغلاق وردية فيها 5 مختلط + 10 عادي → الأرقام تطابق `paymentMethodBreakdown`.
4. إرجاع فاتورة مختلطة → ReturnDialog يتعامل صح (نتحقق إن كان يحتاج تعديل).
5. أوفلاين + سنك.
