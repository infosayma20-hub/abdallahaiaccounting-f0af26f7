## الوضع الحالي

المحاسب الذكي (حسيب) **يدعم اليوم 5 أنواع فقط** من المستندات:
- فاتورة مبيعات • فاتورة مشتريات • سند قبض • سند صرف • قيد يومية

**لا يدعم إنشاء طلبيات (orders) للمتاجر الإلكترونية** — هذه تُضاف فقط يدوياً من `OrderFormPage`. لا يوجد أي ربط بين `process-transaction` Edge Function وجدول `orders`.

---

## الهدف

السماح للمستخدم بقول/كتابة جملة طبيعية مثل:
> *"اعملي طلبية لجليلة من رام الله، رقمها 0599..., بدها 3 قمصان سعر الواحد 50 شيكل، توصيل بكرا، الدفع كاش عند الاستلام، الطلب جاي من انستجرام"*

ويقوم حسيب باستخراج البيانات، يسأل عن الناقص الإلزامي فقط، ثم يُنشئ الطلبية في جدول `orders` تلقائياً ويعرض رابطها.

---

## الخطة

### 1. توسيع تصنيف الأوامر (Intent Classification)
- ملف: `src/lib/multiCommandParser.ts`
- إضافة `'order'` لقائمة `CommandType`
- كلمات مفتاحية: "طلبية"، "أوردر"، "اعملي طلب"، "زبون جديد بده"، "متجر"، "إنستجرام"، "واتساب"، "فيسبوك"، "تيك توك"

### 2. توسيع Edge Function (process-transaction)
- ملف: `supabase/functions/process-transaction/index.ts`
- إضافة فرع جديد للـ `نوع_الحركة = "طلبية"` يستهدف جدول `orders` بدل `invoices`
- توسيع schema الـ JSON المُستخرج بحقول الطلبية:

```json
{
  "نوع_الحركة": "طلبية",
  "اسم_الزبون": "",
  "هاتف_الزبون": "",
  "المدينة": "",
  "العنوان": "",
  "المنصة": "instagram|facebook|whatsapp|tiktok|website|phone",
  "رابط_البروفايل": "",
  "بنود": [{"اسم_الصنف":"","الكمية":1,"السعر":0}],
  "طريقة_الدفع": "كاش|فيزا|تحويل|cod",
  "تاريخ_التوصيل": "YYYY-MM-DD",
  "ملاحظات": "",
  "الحقول_الناقصة": ["..."]
}
```

### 3. حوار توضيحي ذكي (Clarification Flow)
حسيب يسأل **فقط عن الناقص الإلزامي** بسؤال واحد مختصر بالعربية الدارجة:

| إذا ناقص | السؤال |
|---|---|
| اسم الزبون | "شو اسم الزبون؟" |
| الأصناف | "شو بده يطلب وكم الكمية؟" |
| السعر | "كم سعر [الصنف]؟" |

الحقول الاختيارية **لا يسأل عنها** — يتركها فاضية ويُنبّه برسالة:
> "تم ✅ — تذكير: ما حدّدتي مدينة/هاتف، فيكي تكمّليها لاحقاً من الطلبية"

### 4. إنشاء الطلبية في DB
- استدعاء `supabase.from('orders').insert(...)` مع:
  - `order_number`: `ORD-{timestamp}` (نفس منطق `OrderFormPage`)
  - `status: 'جديد'`, `payment_status: 'غير مدفوع'`, `source: المنصة المُستخرجة`
  - `subtotal/total`: محسوبة من البنود
- إنشاء `order_items` لكل صنف
- ربط الزبون: لو موجود في `contacts` يربطه، لو لا يُنشئ contact جديد (تلقائياً مع علم `إنشاء_طرف_جديد`)

### 5. عرض النتيجة في الواجهة
- ملف: `src/components/haseeb/CleanSmartAccountant.tsx`
- رسالة نجاح تعرض: رقم الطلبية + الإجمالي + زر "فتح الطلبية" (ينقل لـ `/orders/{id}`)
- بطاقة ملخص فيها: اسم الزبون، عدد الأصناف، الإجمالي، المنصة

### 6. تحديث System Prompt
إضافة قسم في الـ prompt يشرح:
- متى يُنشئ طلبية بدل فاتورة (الفرق: الطلبية = وعد بيع لم يُحاسَب بعد، الفاتورة = مبيعات مُرحّلة محاسبياً)
- قواعد استنتاج المنصة من السياق
- لا يُنشئ قيد محاسبي للطلبية (الطلبية ليست مستند محاسبي حتى تتحول لفاتورة)

### 7. أمثلة تدريبية في الـ Prompt (Few-shot)
3 أمثلة جاهزة في الـ system prompt لتثبيت السلوك:
- طلب من إنستجرام كامل المعلومات
- طلب ناقص (اسم + صنف بس) → يسأل عن السعر
- طلب متعدد الأصناف من واتساب

## التفاصيل التقنية

**ملفات سيتم تعديلها:**
- `src/lib/multiCommandParser.ts` — إضافة intent `order`
- `supabase/functions/process-transaction/index.ts` — فرع جديد + توسيع schema + system prompt
- `src/components/haseeb/CleanSmartAccountant.tsx` — معالجة استجابة الطلبية وعرضها
- `src/components/haseeb/MobileSmartAccountant.tsx` — نفس المعالجة للجوال

**ملفات بدون تعديل (مرجع فقط):**
- `src/pages/OrderFormPage.tsx` — مرجع للحقول والافتراضيات
- جدول `orders` و `order_items` في DB — موجودان جاهزان

**لا حاجة لـ migrations** — الجداول موجودة.

## معايير القبول

1. قول "اعملي طلبية لـ X من Y بـ Z أصناف" يُنشئ طلبية تظهر فوراً في `/orders`
2. لو نقص الاسم أو الأصناف → حسيب يسأل سؤال واحد مختصر
3. لو الزبون موجود في `contacts` يُربط، لو لا يُنشأ تلقائياً
4. الطلبية لا تُنشئ قيد محاسبي (يبقى ذلك حصراً على الفاتورة)
5. الواجهة تعرض زر "فتح الطلبية" مباشرة بعد الإنشاء
