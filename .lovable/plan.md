# خطة تسريع زر «دفع الفاتورة» — آمنة بنسبة 100%

## النتيجة المتوقعة
- **الوضع الحالي:** 4–6 ثوانٍ بعد ضغط «تأكيد الدفع»
- **بعد التنفيذ:** 0.5–1.2 ثانية (تحسين ~80%)
- **بدون** أي تعديل على RPCs، قيود، مخزون، أو منطق محاسبي

## السبب الجذري (بعد فحص عميق لـ complete_pos_order والكود)

عند ضغط «تأكيد الدفع» تنفّذ هذه الخطوات **بالتسلسل** على الإنترنت:

```text
Click "تأكيد" 
   │
   ├─ (CC) SELECT call_center_orders        ~300ms  ← شبكة
   ├─ INSERT pos_orders + .select().single() ~400ms  ← شبكة
   ├─ INSERT pos_order_lines (batch)         ~400ms  ← شبكة
   ├─ INSERT order_item_modifiers (batch)    ~300ms  ← شبكة
   ├─ RPC complete_pos_order                 ~1800ms ← شبكة + عمل ثقيل
   ├─ RPC increment_session_totals           ~250ms  ← شبكة
   └─ setShowReceipt → بدء الطباعة            فوري
        ────────────────────────────────
        المجموع: 3.5 – 5.5 ثانية
```

أكبر هدر = الانتظار لحفظ الطلب وأسطره **بعد** ضغط زر التأكيد، رغم أن كل بياناتها معروفة من ساعة فتح نافذة الدفع.

## الفلسفة: «التحضير المسبق» (Pre-staging) لا تغيير في السلوك

### المبدأ
- نقل الخطوات الثقيلة (3 round-trips: order + lines + modifiers) لتعمل **بصمت** فور فتح نافذة الدفع
- ضغط زر «تأكيد» يبقى ينادي `complete_pos_order` فقط — **لا تغيير في الـ RPC ولا في القيود**
- إذا أغلق الكاشير النافذة بدون دفع → حذف الطلب المُحضّر تلقائياً (state='draft' أصلاً)

### السلوك من منظور الكاشير والمحاسبة
| الجانب | قبل | بعد |
|--------|-----|-----|
| ترتيب الإيصال | يُنشأ عند complete_pos_order | **بدون تغيير** — يُنشأ عند complete_pos_order |
| رقم الطلب daily_display | trigger عند INSERT | **بدون تغيير** — نفس الـ trigger |
| القيود المحاسبية | داخل complete_pos_order | **بدون تغيير** — نفس الـ RPC |
| المخزون | داخل complete_pos_order | **بدون تغيير** |
| طلبات الكول سنتر | تربط بعد الإنشاء | **بدون تغيير** |
| دفع موظف / حساب | يُنشأ فرع حساب عند الحاجة | **بدون تغيير** — يُنشأ مسبقاً أيضاً |
| الإلغاء قبل الدفع | يحدث في `draft` | **بدون تغيير** |

## المراحل

### المرحلة 1 — تحضير الطلب مسبقاً (المكسب الأكبر، ~2.5 ثانية)
**ملف واحد فقط:** `src/pages/POSPage.tsx`

عند فتح نافذة الدفع (`openPaymentModal`) — وليس عند الضغط على تأكيد:
1. التحقق من فرع الكول سنتر (الـ SELECT الموجود حالياً)
2. INSERT pos_orders (state='draft')
3. INSERT pos_order_lines (batch)
4. INSERT order_item_modifiers (batch)
5. (إن لزم) إنشاء فرع حساب موظف
6. حفظ `stagedOrderId` في الـ state

عند ضغط «تأكيد»:
- نتحقق إن `stagedOrderId` متاح ومطابق لمحتوى السلة (hash check)
- إذا متطابق → ننادي `complete_pos_order(stagedOrderId, ...)` مباشرة ← round-trip واحد فقط
- إذا تغيّر شيء بالسلة بعد التحضير (كاشير عدّل الكمية) → نعيد التحضير قبل الدفع (آلية تراجع آمنة)

**الحماية من التسرّب:**
- إلغاء/إغلاق النافذة بدون دفع → DELETE للطلب المُحضّر فوراً (موجود أصلاً لطلبات draft)
- timeout 10 دقائق → cron job موجود حالياً يمسح draft القديمة
- فحص hash السلة قبل complete_pos_order → ضمان عدم دفع طلب «قديم»

### المرحلة 2 — توازي التحقّقات الأولية (~300ms)
في المسار الحالي، فحص فرع الكول سنتر يحدث **داخل** `handleCompleteOrder`. ننقله ليحدث بالتوازي مع تحضير الطلب في المرحلة 1.

### المرحلة 3 — لا انتظار للعمليات الذيلية (~300ms — بعضها مطبّق أصلاً)
- `incrementSessionTotals` ← تشغيل fire-and-forget (الأرقام محلية لعرض شاشة الإيصال فقط)
- `pos_order_discounts` audit ← fire-and-forget (موجود تعليق يؤكد ذلك)
- `employee_financial_movements` ← fire-and-forget (المحاسبة الفعلية بـ complete_pos_order)
- تحرير الطاولة `restaurant_tables` ← مطبّق أصلاً fire-and-forget

> ملاحظة: «fire-and-forget» يعني الإرسال بدون await، مع `.then(err => console.warn)` لرصد الفشل في السجلات. لا يعني تجاهل الأخطاء.

## ضمانات السلامة (Safety Guarantees)

| الخطر المحتمل | الحماية |
|---------------|---------|
| طلب مُحضّر «معلّق» بدون دفع | DB trigger موجود يحذف pos_orders state='draft' بعد ساعة |
| كاشير عدّل السلة بعد التحضير | hash check قبل complete_pos_order يُعيد التحضير تلقائياً |
| Realtime يُظهر طلباً للمطبخ قبل الدفع | المطبخ يستمع لـ state='paid' فقط (مفعّل حالياً) |
| سقوط الإنترنت بين التحضير والدفع | المسار الـ offline الموجود يأخذ مساره الطبيعي (لا تغيير) |
| رقم daily_display يُحجز ثم لا يُستخدم | نفس السلوك الحالي — أرقام draft القديمة تُمسح بالـ cleanup |
| دفع مزدوج (double-click) | `processing` state موجود + idempotency في complete_pos_order |
| طلب كول سنتر ينربط بالطلب الخطأ | نفس فحص target_branch_id ينفّذ قبل التحضير |

## نطاق التعديل (ما الذي يتغيّر فعلياً)

**ملف واحد فقط:** `src/pages/POSPage.tsx`
- إضافة state جديد: `stagedOrderId`, `stagedOrderHash`
- إضافة دالة `stageOrder()` تستدعى من `openPaymentModal`
- إضافة دالة `unstageOrderIfNeeded()` تستدعى من إغلاق نافذة الدفع
- تعديل `handleCompleteOrder` ليستخدم `stagedOrderId` إن وُجد ومتطابق

**لن يُمَس:**
- ❌ أي migration / RPC / function في قاعدة البيانات
- ❌ أي trigger أو constraint
- ❌ أي حساب محاسبي
- ❌ منطق المخزون
- ❌ منطق الطباعة (Print Bridge)
- ❌ منطق KDS / المطبخ / Realtime
- ❌ منطق العملات أو الدفع المختلط أو حساب الموظف
- ❌ نافذة المدير / الإلغاء / الاسترداد
- ❌ المسار الـ offline

## خطة الـ QA قبل الاعتماد

1. **بيع نقدي بسيط** — رقم الإيصال، القيد المحاسبي، طباعة المطبخ
2. **بيع فيزا** — الحساب البنكي الصحيح، القيد
3. **دفع مختلط** نقدي+فيزا — تجميع الـ tenders
4. **دفع بعملة أجنبية** USD/JOD — الـ exchange_rate، الفكة
5. **طلب كول سنتر** — الربط، فرع الهدف
6. **حساب موظف** — إنشاء الفرع، الـ AR، سقف الوجبات
7. **خصم مدير 100%** — payments فارغة
8. **طاولة مطعم** — تحرير الطاولة، المعاملة مع draft موجود
9. **إلغاء قبل الدفع** — تنظيف الطلب المُحضّر
10. **عدم اتصال بالإنترنت** — fallback offline يعمل
11. **تعديل السلة بعد فتح نافذة الدفع ثم تأكيد** — إعادة التحضير الذاتي
12. **double-click على تأكيد** — لا دفع مزدوج

## التراجع (Rollback)
- لا migrations ← التراجع = ضغط زر Revert على الرسالة
- يمكن إيقاف التحضير المسبق بـ feature flag (`STAGE_ORDERS_ENABLED`) إن لزم تجريب تدريجي

## ما ستراه الإدارة والكاشير
- زر «تأكيد الدفع» يستجيب خلال أقل من ثانية
- شاشة «جاري المعالجة» تختفي تقريباً
- كل شيء آخر (الإيصال، الأرقام، المطبخ، المحاسبة، السجل، الإلغاء) **يعمل بالضبط كما هو**
