# POS Rules

- POS boot: `initializePOS` fetches tenant/user lookups in one parallel batch (products/rates start immediately), `POSDeviceAuthGuard` mounts POS under the shared `POSBootOverlay` while device checks run (no shift claim until the guard resolves via `posBootLoading`), and the offline pre-cache is deferred 20s. Why: entry used to serialize ~15 round-trips plus the bridge probe.
- POS v2 (`/pos-v2`) is the same `POSPage` with `variant="v2"`: only the top bar, products and cart zones swap to `src/components/pos/v2/*`, fed by the existing state/handlers; v2 theme/card size live in React state only. Why: a UI experiment must never fork sales/print logic or change `/pos`.
- POS v2 invoice history reuses `InvoiceHistoryDrawer` with `experimentalLayout`: presentation becomes a side-by-side list/detail workspace while all invoice actions remain shared; shift closure is a dedicated top-bar action. Why: visual experiments must not fork audited invoice or shift workflows.
- POS v2 is the default for every POS user, with legacy `/pos` available for the current tab; both category and product sorting reuse the shared handlers and `pos_user_preferences`, and both interfaces use the same non-`الكل` initial-category rule. Why: preserve each cashier's layout while keeping one sales and printing workflow.
- POS v2 top bar auto-hides (wrapper height 0) and reappears on mouse at the top edge (window `mousemove` listener, clientY ≤ 12) or when `PendingOrdersPanel` reports pending call-center orders via `onPendingCountChange`; the demo banner in `POSDeviceAuthGuard` auto-hides after 6s. Why: small square POS screens need maximal cart/product space without losing alert visibility.
- Multi-business tenants: `business_units` groups branches/warehouses; `product_business_units` limits a product to units (no rows = shared). POS hides other-unit products from the grid only (scans still resolve), cached per branch in localStorage. Why: lighten each shop's POS without forking products or touching history.

- Purchase amount entry derives unit price from an editable total without premature rounding and retains the existing purchase RPC. Why: keep supplier, cash and stock posting unchanged.
- POS screen/print language: `pos_terminals.receipt_language` (set in the new-device wizard) wins, else `branches.receipt_language`, else ar. Why: per-station config.
- POS expenses are cancelled only via RPC `pos_cancel_expense_v1` (admin, mandatory reason): it posts a mirror reversal with `create_reverse_entry` and flags `pos_expenses.cancelled_at`; every shift/cash sum must exclude cancelled rows. Why: never delete posted cash entries.
- POS purchases (`pos_purchases.supplier_id`) reference `contacts` suppliers, not `pos_suppliers`; `pos_record_purchase_v1` validates and posts against the contact. Why: the supplier ledger/statement lives on contacts.
- Closed-shift corrections (change/split payment, void invoice, cancel purchase/expense) go only through `pos_shift_*_v1` RPCs gated by `_pos_shift_correction_gate` (company flag `company_settings.pos_shift_corrections_enabled`, owner-admin or `accountant_permissions.can_pos_shift_*`, closed shift, audit not approved, reason ≥3); they set the transaction-local `app.pos_shift_correction` flag to pass the open-shift guards and log to `pos_shift_post_close_edits`. Why: reuse the audited POS GL/stock paths instead of forking them.
- POS sales returns go only through RPC `pos_return_v2` (gated server-side by `pos_user_permissions.can_pos_return` or tenant owner/admin; cancel stays on `can_cancel_invoices`): refund is cash or the original single payment account, damaged lines restock then post a `pos_return_damage` stock-out and damage-expense GL. Why: returns must be permissioned and post stock/GL in one audited path.
