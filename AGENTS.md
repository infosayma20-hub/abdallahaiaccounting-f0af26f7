# Project Rules

- Use “يونيفاي” / “UNIFY” exclusively in all user-facing forms, documents, printouts, emails, notifications, and defaults; retain legacy `amwali` identifiers only where changing them would break storage, routes, database objects, integrations, or historical links.- Barcode goods receiving writes only via SECURITY DEFINER RPCs (`receiving_*`, `assign_receiving_session`) on `procurement_receiving_*`; stock/GL stay in the existing purchase-invoice flow. Why: workers must not see prices or post financials.
- Purchase order lines reference `procurement_items` (purchasing catalog); stock always goes to `procurement_items.inventory_product_id` via `ensure_procurement_item_product`, and invoice lines carry `procurement_order_item_id` for cumulative received qty. Why: order item ids are not products ids (FK failed silently before).
- Warehouse receiving is a standalone employee workspace: entry requires an active receiver flag or an assigned receiving session, and its back action returns only to the workspace chooser. Why: prevent warehouse staff from falling into the administrative ERP shell.
- Employee hot-drink sales use the dedicated atomic RPC and `[EMPLOYEE_HOT_DRINK]` order-line marker; the first two drinks per POS business day are half price, later drinks are full price, and all marked lines bypass stock movements. Why: keep limits, employee debt, and inventory treatment auditable and race-safe.
- Attendance rules (timezone Asia/Hebron, 06:00 business-day start, gap/grace/tolerance/cap defaults) live only in DB function `attendance_departure_rules()`; `recompute_attendance_day`, `hr_backfill_attendance` and the UI (`applyAttendanceRules` via `useDepartureCap`) read from it. Why: one source of truth.
- HR attendance edits never mutate raw `attendance_events`: they go only through RPC `hr_save_attendance_day`, which stores corrections in `attendance_day_overrides` (in/out, status lock for leave/absent/holiday, ignored punch ids, linked leave), applies explicit break diffs and gap dismissals, recomputes via `_attendance_effective_events`, and audits — all in one transaction. UI times are built in Asia/Hebron via `src/lib/hebronTime.ts`. Why: same-day edits stay correct when new punches arrive, and every change is reversible and auditable.
- POS screen/print language comes only from `branches.receipt_language` (admin, default ar). Why: no impact on other branches.
- Daily cloud backup (retention: last 30 daily folders per tenant, older dated folders deleted at end of each run; `الملفات` never pruned): edge function `cloud-backup` (pg_cron `cloud-backup-daily`, 02:00 UTC = 05:00 Hebron summer time) writes read-only per-tenant exports to Backblaze B2 `unifyerp-storage` under `العملاء/<company>__<owner8>/النسخ-الاحتياطية/YYYY/MM/DD/<category>/<table>/part-NNN.json` plus incremental `الملفات/<bucket>/<path>`; resumable in 40s slices via `cloud_backup_runs.state`, auth via `cloud_backup_config.cron_token`. Why: stay under edge CPU limits and keep each tenant isolated and organized.
- Purchase-order edits go only through RPC `update_procurement_order` (gate: `procurement_order_edit_block_reason`), which keeps line ids, forbids qty below invoiced qty or deleting received lines, and logs before/after in `procurement_order_edits`. Why: edits must never break receiving/invoice links and must be auditable.
- Direct receiving (no prior PO): employees with `employees.can_direct_receive` create/scan/price/submit only via `direct_receiving_*` RPCs on `procurement_orders` (`source='direct_receiving'`, `review_status` in_progress→pending_review→approved/rejected); submit creates a `submitted` receiving session so the existing invoice flow posts stock/GL; temp lines (`product_id IS NULL`, `temp_barcode`) must be linked via `direct_receiving_link_temp_line` before invoicing. Why: daily deliveries without accountant pre-orders while keeping finance in one audited path.
- Camera barcode scanning uses one shared component (`POSBarcodeScanner`): native `BarcodeDetector` when available, else the `barcode-detector` ponyfill (ZXing-C++ WASM served locally from `public/zxing/`, must match the installed zxing-wasm version); scan inputs normalize via `src/lib/barcode.ts` and are processed serially; server scan RPCs match through `_barcode_variants()` (Arabic digits, spaces, UPC-A/EAN-13 leading zero). Why: fast, offline-capable decoding and no dropped/mismatched scans.

- Barcodes are unique per tenant across products.barcode and product_barcodes (trigger enforce_unique_product_barcode); one product may have many barcodes. Why: a scan must resolve to exactly one product.
- Fresh sign-ins keep the login screen visible under the global welcome overlay while `/apps` preloads invisibly; navigation occurs only after auth, roles, company/card settings, app overrides, card gates, and the full success animation settle, with a watchdog fallback. Why: users never see an intermediate loading screen and land on complete cards.
